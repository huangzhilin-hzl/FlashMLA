# 当前实现与优化结论

目标固定为 B300 GPU1 上的 `b8192, s_q1, H64, Dqk576, Dv512, TopK2048`，
输入 Q/KV 为 E4M3 FP8，输出 BF16。原始测试脚本、参考计算和误差阈值保持不变。

目前默认快速版本是 **v146**。在已记录的四轮同进程换序 Graph 测试中，暖缓存约
1.671–1.673 ms，配对 TRTLLM 约 1.872–1.879 ms，速度比约 1.119–1.124 倍。
这是该执行方式下的实测结果；短事件测试和有主机间隙的长事件测试不能直接混比。

快速版本并非完整 FP32 参考检查零误差：两个全量种子分别有 9 和 6 个元素超出
原始容差，与 TRTLLM 的失败位置和数值相同；短序列和带空洞索引的误差更明显。
需要完整容差通过时，当前高精度版本是 **v160**。两组全量种子、全量短序列和
带空洞输入均与 v153 逐位一致，保留了 v148 重新执行的全量 FP32 检查通过结论。
它进一步将 score 缩放从 32 条标量乘法改为 16 条 packed 乘法，四轮暖缓存约
1.8615–1.8618 ms，比 v153 快约 6–10 μs，冷缓存三轮更快、一轮慢约 3.8 μs。
同轮 TRTLLM 暖缓存约 1.866–1.878 ms。换序冷缓存中有一轮仅快 0.1 μs，视为接近；
独立 Graph 长测的暖缓存仍落后于 TRTLLM，因此不宣称所有执行方式都领先。

v129/v133 分别在快速/高精度版本上把输出的 L2 淘汰优先级设为 evict-first。
v141 则把同样的输出策略叠加到 v138 上。三者都已通过两组全量种子、短序列和
空洞输入的逐位等价验证。收益较小且与执行
方式有关，因此先作为备选，不替换默认版本。v129 的一组硬件采样显示 DRAM
读取量减少约 8.8%；这不意味着端到端延迟也会同比下降。

v146 在 v138 上把位图读取提前到 QK 等待之前；SASS 确认了指令位置变化，
四轮暖/冷缓存均快于 v138，完整逐位验证也保持一致。

v152 叠加早读位图后，三轮暖缓存比 v148 快约 7–8 μs，冷缓存两胜一负。
完整逐位检查保留了 v148 的精度结论；后续 v153 改进同步，v160 再叠加 packed 缩放。快速路径的 v150 合并生产者同步
后表现随测试顺序变化，v151 删除多余 fence 没有短测收益，均未替换默认版本。

近期实验支持以下判断：

- 当前流水线需要优先提交已就绪的 PV。强制等待未来 KV 并提前 QK 的 v131
  退步到 2.038 ms；根据 KV 就绪状态选择提交顺序后，v132 回到 1.661 ms，
  合并通知的 v134 为 1.653 ms，但都未改善默认版本。
- 直接 256 位输出写回确实减少了共享内存中转。源码计数器对这种写指令报告的
  理论 sector 数不能按字面解释；硬件计数器确认输出流量仍是 512 MiB。
- 共享内存冲突的聚合计数不等于实际指令布局冲突。当前源码采样的实际与理想
  shared wavefront 数相同，excessive 为零，不能据聚合计数盲目改 swizzle。
- 默认 NCU 时钟控制曾逆转候选排序。性能排序使用未插桩配对测试；NCU 的基准
  时钟数据用于诊断，并另用解锁时钟采样确认等待位置。
- v135 的 256 列 TMEM 复用方案被 Tensor Core 访问检查拒绝，没有性能结果。
  保守分配 512 列的 v136 通过访问检查，但耗时 2.960 ms。静态元素映射和较高
  resident warp 数，都不能单独证明两个 CTA 正在并行做有效计算。
- 原生 x64 TMEM 加载与寄存器重分配的组合仍有编译失败。v138 改用两次 x32
  加载后合并等待，使用 123 个寄存器、零栈，NCU 确认零 local-memory 流量。
  迁移到高精度路径的 v140 和用于最终输出加载的 v142 均未取得短测收益。
  v138 的两组全量种子、短序列和空洞输入均与 v125 逐位一致，四轮暖/冷缓存换序均
  快于 v125。它减少了约 0.54% 的动态指令，实际时延收益也较小。
